## 1. P1 — real risk, fix before the next release

### P1-1 · CI never runs two of the test files (regression already documented, unfixed)
`ci.yml:111-117` enumerates directories:

```
flutter test test/data/ test/presentation/ test/core test/features test/shared --coverage
```

`test/main_test.dart` and `test/widget_test.dart` exist at `test/` root and are therefore **never
executed in CI**. `Makefile:20-22` documents this exact bug as fixed — the fix went into `make test`
(`flutter test --coverage`, whole directory) and **never propagated to CI**. A startup-path
regression in `main.dart` boot order, encryption init, or `ProviderScope` wiring can merge green.
*Fix:* replace the list with `flutter test --coverage`.

### P1-2 · The release gate's evidence is gitignored
`docs/release-evidence/v1.2.1-rc.2/gate-android-small_phone.log` and
`gate-ios-iphone17pro.log` are **not tracked** — swallowed by the blanket `*.log` rule
(`.gitignore:3`). **REPORTED** by the tooling scout, path existence confirmed. `AGENTS.md` (§Release
gate) requires the pass to be *recorded*; a record that cannot be committed is a record that can be
silently lost. *Fix:* `!docs/release-evidence/**/*.log` negation, or commit evidence as `.txt`.

### P1-3 · `.gitignore:15-16` un-tracks the iOS project if anything is ever re-staged
`*.pbxproj` and `*.xcworkspace` are ignored, yet `ios/Runner.xcodeproj/project.pbxproj` and
`ios/Runner.xcworkspace/{contents.xcworkspacedata,xcshareddata/*}` are tracked — they survive **only**
because they were committed before the patterns were added. Verified:

```
$ git check-ignore -v --no-index ios/Runner.xcworkspace
.gitignore:16:*.xcworkspace   ios/Runner.xcworkspace
```

Any `git rm -r --cached ios/` + re-add (a routine operation during a CocoaPods or signing rework)
**silently drops the Xcode project from the repo** — an unbuildable iOS release with a green diff.
*Fix:* delete those two lines (they are not Flutter defaults; they were hand-added).

### P1-4 · `make ci` and CI are not the same gate
| In CI, absent from `make ci` | In `make ci`, absent from CI |
|---|---|
| `Check version sync (AppConfig vs pubspec)` (`ci.yml:97`) — **no Makefile target exists at all** | `store-check` (`Makefile:13`) — `store/v1.2.1/check.py` **never runs in CI**, though `AGENTS.md:120` lists it as part of the pipeline |
| Trivy / Gitleaks / Semgrep (`ci.yml:42,61,55`) — targets exist but are not prerequisites of `ci:` | whole-`test/` coverage (see P1-1) |
| Integration smoke + `flutter drive` (`integration-tests-local`) | coverage-missing guard: CI has `if [ ! -s … ]; then exit 1`, `Makefile:45-49` has **no `-s` guard** → a missing report becomes a `[ "" -ge 80 ]` shell error |

So "it passes locally" and "it passes on CI" currently mean different things in both directions.
*Fix:* one `gate` target that mirrors CI, and CI calls `make gate`.

### P1-5 · 26 relative imports resolve outside the repo root — they work only by clamping
Verified mechanically over all 117 files: 26 imports in 9 files resolve to a path **outside `lib/`**,
and the analyzer/compiler clamps them back to the package root. Reproduced:

```
lib/core/router.dart:5   import '../../features/growth/...'   → <repo>/features/... (MISSING) — analyzes CLEAN
lib/core/zz_bad.dart     import '../../features/nope...'      → error: uri_does_not_exist
```

i.e. the depth is wrong (from `lib/core/` the correct prefix is `../features/`, not `../../features/`)
and only a nonexistent *final segment* triggers a diagnostic. `router.dart` alone carries 10;
`lib/core/l10n/date_localization.dart`, `lib/core/providers/active_baby_provider.dart`,
`lib/data/local/tracking_event_mapper.dart`, `lib/shared/utils/health_label_resolver.dart`,
`lib/features/{home,menu,reminders}/…` carry the rest.
*Fix:* normalise depth, or switch these 9 files to `package:mamadera/…` imports (requires
`prefer_relative_imports` handling in `analysis_options.yaml:53`). Zero behaviour change, so
`flutter analyze` + `flutter test` are sufficient proof.

## 2. P2 — architecture and structure

### P2-1 · Two `domain/` files depend on Flutter (breaks the stated rule)
`AGENTS.md`: *"Domain layer: pure logic, zero framework dependencies."* Verified violations — **exactly
two files**, enumerated by `grep package:flutter` over every non-generated file under `*/domain/*`:

1. **`lib/shared/domain/entities/tracking_icons.dart`** (90 L) — **100 % presentation, zero domain
   logic.** Extensions mapping enums to `IconData` (`TrackingType.icon => Icons.lunch_dining`,
   `FeedingSubtype.icon => Icons.local_drink_outlined`, `WasteType`, …). No `dbValue`, no validation,
   no rule. It sits in `shared/domain/entities/` only because `tracking_enums.dart` is next door.
   6 `lib/` consumers — **all of them in `presentation/`** — plus `test/shared/domain/entities/tracking_icons_test.dart`.
2. **`lib/features/growth/domain/entities/measure_kind.dart`** (150 L) — a **genuinely domain enum**
   (`poids`/`taille`/`temperature` with `dbValue`, `unit`, `min`/`max` validation ranges, `decimals`,
   `labelKey`, `fromDbValue`) carrying exactly **one** UI field: `icon` (`:18,29,40` —
   `Icons.scale_outlined`, `Icons.straighten`, `Icons.thermostat`).

**Correction (2026-10-19):** `lib/shared/domain/entities/quantity_unit.dart` does **not** import
Flutter — it imports `../../../data/local/db_constants.dart` (`:1`), which is a P2-2 leak, not a P2-1
one. An earlier pass of this audit said three files; the verified number is two. `measure_kind.dart:4`
makes that same file a P2-2 case too.

**The repo already contains the correct pattern for case 2:** accent colours for the same enum live in
`lib/features/growth/presentation/widgets/measure_kind_accent.dart` as
`extension MeasureKindAccent on MeasureKind`, whose own doc comment reads *"the domain is not familiar
with…"*. Decorate-by-extension is established convention here; the `icon` field is the one deviation.
See §5 — fixing case 2 costs **zero** import changes at the call sites.

### P2-2 · Presentation reads `data/local/` directly (3 files)
`lib/features/home/presentation/providers/track_notifier.dart`,
`lib/features/reminders/presentation/widgets/custom_reminder_form_sheet.dart`,
`lib/features/reminders/presentation/widgets/reminder_row.dart` import
`../../../../data/local/db_constants.dart`. Low harm (constants), but it is the leak the repository
pattern exists to prevent, and `AGENTS.md` says presentation depends on repository providers *only*.
The same leak runs one layer deeper from `domain/`: `measure_kind.dart:4` and `quantity_unit.dart:1`
import `../../../data/local/db_constants.dart` — five files total.

### P2-3 · Cross-feature coupling hotspots (import graph)
`core/router.dart` importing every feature is correct and expected. The ones that are not:
`history/presentation → growth/{domain,presentation}` (4 + 3), `home/presentation → reminders/presentation`
(3) + `→ reminders/domain` (2), `menu/presentation → baby/presentation` (2),
`menu/presentation → history/presentation` (2), `import/presentation → history/presentation` (2),
and `core/providers/active_baby_provider → features/baby/presentation` — **`core/` reaching up into a
feature's presentation layer**, an inverted dependency. Track as a ratchet (see §4).

### P2-4 · Test tree has two competing conventions
`AGENTS.md` prescribes `test/features/<module>/<layer>/`. Both trees are live, and there are
**duplicate basenames** across them: `tracking_repository_impl_test.dart`, `update_delete_test.dart`,
`update_delete_test.mocks.dart` exist in both `test/data/repositories/` and `test/features/*/…`.
Legacy flat tree: `test/data/`, `test/presentation/`, `test/shared/`. Duplicates are how a test gets
updated in one tree and forgotten in the other.

### P2-5 · `lib/` ships three entry points
`lib/main.dart` (app), `lib/driver_main.dart` (Flutter Driver target, referenced by CI
`--target=lib/driver_main.dart`), `lib/asc_driver_main.dart` (275 lines, store-screenshot driver).
The two driver entry points compile into the app tree. They are build-time dead weight in a release
binary whose APK size is a tracked concern. *Fix:* move to `test_driver/` or `tool/`, or document the
reason they must live in `lib/`.

### P2-6 · Driver/harness tree tripled
`integration_test/` (14 files) + `test_driver/` (8 files) + `lib/*_driver_main.dart`, including
one-off release-gate scripts (`integration_test/v121_upgrade_verify.dart`,
`integration_test/entry_sheet_gate_rc4.dart`, `integration_test/pickers_gate_rc2.dart`,
`test_driver/v121_upgrade_verify.driver.dart`). These are RC-gate artefacts for releases that shipped.
Keep the 6 flow suites + `ci_smoke_suite.dart` + `screenshot_capture.dart`; archive the RC-specific ones.

## 4. "Some sort of sonar" — recommendation

Do **not** stand up SonarQube. Measured/verified reasoning:

1. **SonarQube Community Build has no official Dart support.** SonarSource sells Dart/Flutter in
   paid editions; the community path is `insideapp-oss/sonar-flutter`, whose latest release is
   **2024-09-07** (via `sx`, corroborated by `sonarplugins.com`). A 2-year-old plugin against the
   2025+/2026 plugin API is a self-inflicted outage waiting to happen. GitHub API detail:
   **NOT VERIFIED** (rate-limited from this Mac).
2. **It duplicates what is already green here.** `flutter analyze` with `strict-casts`,
   `strict-raw-types`, `strict-inference` and ~130 explicit lints (`analysis_options.yaml`) already
   returns zero issues; Trivy, Gitleaks and Semgrep already run blocking in `ci.yml:42,55,61`.
3. **Cost:** a JVM server + database, on a free-tier account whose integration job already cannot
   fit a 55-minute emulator run on a 2-core runner (`ci.yml` job notes).

What to add instead — a **~30-second local+CI gate, no new service**, in the spirit of the audit:

| Gate | Tool | Blocks on |
|---|---|---|
| `make gate` | mirrors CI exactly (P1-4) + `store-check` | anything CI blocks on, plus what only CI checks today |
| Structure ratchet | ~80-line `scripts/check_architecture.py` — the import-graph logic from this audit | (a) any `domain/` import of `flutter/*` **above** the current count of 3, (b) any `presentation → data/local` import **above** 3, (c) any relative import resolving outside `lib/` (currently 26 → target 0), (d) any new `core → features/*/presentation` edge |
| Complexity | `lizard` (already runs via `uv tool run`, no install) | CCN > 25 today's worst is 31 → set 30 and ratchet down; NLOC > 150 |
| Widget length | resurrect the orphaned `scripts/check_function_length.py` — or delete it | the `AGENTS.md` ~25-line rule, currently unenforced |
| Format | `dart format --output=none --set-exit-if-changed` | drift (currently **not checked anywhere**) |
| Docs links | the `test -e` loop from §3 | new broken links |

A ratchet (fail on *new* violations, with the current counts pinned in a baseline file) is what makes
this stick: it costs nothing today, catches everything tomorrow, and needs no infrastructure. If a
dashboard is genuinely wanted later, DCM (`dcm.dev`) is the maintained Dart-metrics tool — **but verify
its licensing** first; it went commercial and I did not confirm current terms.
